Convenios: rediseño móvil e inmediatez

Auditoría completa de la experiencia PWA para teléfonos, contrastada con docs/sistema-diseno-mobile (1).md, el código actual, la PWA ejecutada en Chrome y la documentación de Next.js 16.3 instalada. Define el trabajo de UI, navegación, rendimiento, accesibilidad, instalación, conectividad y pruebas sin modificar la interfaz desktop.

Dictamen Alcance Sistema móvil Rendimiento Pantallas Issues Ejecución

Dictamen ejecutivo

La base PWA es válida; la capa móvil todavía no cumple la experiencia definida y debe tratarse como un rediseño propio, aislado del escritorio.

Infraestructura PWABuena base

Manifest, iconos, standalone, Serwist, página offline, borrador de venta y safe areas parciales ya existen.

UI contra especificaciónBrecha alta

Header fijo, barra inferior pegada, cards con bordes/sombras, controles pequeños y modales heredados contradicen la línea móvil.

Sensación instantáneaIncompleta

Hay loading boundaries y prefetch, pero no existe baseline móvil, prueba de navegación instantánea, RUM ni presupuesto de JS.

Verificación móvilParcial real

Se recorrieron en Chrome las rutas permitidas al rol en 390×844 px y el baseline desktop en 1440×900 px. Aún faltan dispositivo físico, instalación y teclado real.

Fortalezas que se conservan

Server Components en páginas, loading.tsx para casi todas las rutas, dashboard con Suspense, prefetch en navegación, borrador local de venta, archivos privados, inputs de 16 px en la base, 100dvh, viewport-fit=cover, icono maskable y soporte explícito para reduced motion en varias piezas.

Riesgo dominante

Modificar primitivas compartidas para conseguir el móvil deseado puede alterar silenciosamente el desktop ya aprobado. El rediseño debe introducir variantes móviles o reglas bajo lg, y cada issue debe pasar una comparación desktop antes/después.

Decisión senior

No reescribir pantallas una por una desde el inicio. Primero construir el shell, tokens, navegación, sheets, estados y pruebas móviles; después migrar las pantallas por flujo de negocio.

Alcance, evidencia y límites

El análisis cubre las 15 rutas visibles, componentes compartidos, estilos, PWA, manifest, service worker, navegación, formularios, archivos y pruebas.

Evidencia inspeccionada

src/app/globals.css, layouts, manifest, service worker, Serwist, shell, 70 módulos cliente, 11 loading boundaries específicas, 15 páginas, componentes de UI, pruebas E2E, baseline desktop, guía móvil y documentación local de Next.js 16.3 sobre PWA, offline y prefetch.

Comprobaciones ejecutadas

npm run check aprobó tipos, lint, formato y 138 pruebas; 51 pruebas con BD quedaron omitidas por su configuración. El build no pudo cerrarse en este entorno porque Turbopack intentó abrir un puerto interno; antes también reveló una dependencia de red en Google Fonts.

Inspección dinámica

Chrome conectado, sesión autenticada y servidor Next.js 16.3 en desarrollo. Se verificaron dashboard, ventas, detalle, empleados, sedes, empresas, convenios, usuarios, auditoría, perfil, contraseña y fallback offline a 390×844 px; además se fijó el baseline del dashboard a 1440×900 px. No hubo overflow horizontal del documento, pero sí contenido recortado dentro de cabeceras, filtros y acciones.

Límites pendientes

El rol actual redirige /ventas/nueva al dashboard y la sesión autenticada impide observar /login. Quedan como verificación de QA la instalación real, standalone, safe areas de iPhone, teclado virtual, gestos, pérdida de red, actualización del service worker, Lighthouse y métricas de una compilación de producción en dispositivo físico.

Auditoría de inmediatez y PWA

“Instantánea” se define con feedback, shell navegable y datos que llegan sin bloquear la transición; no solo con un spinner rápido.

Navegación

Las rutas dinámicas tienen loading.tsx y los destinos principales usan Link con prefetch, lo que permite precargar shells. Sin embargo, no existe una prueba instant(), el cache dinámico cliente está apagado por defecto y ventas desactiva prefetch en una transición de dirección. Debe medirse antes de activar Cache Components o Partial Prefetching; la adopción será incremental, no un flag global sin pruebas.

JavaScript y dependencias

Hay 70 módulos cliente. recharts ya se carga como isla dinámica, pero PDF, formularios grandes y clientes de 1,389/1,277 líneas requieren análisis de chunks. La pantalla de nueva venta depende de Google Fonts durante build; se debe usar stack del sistema o fuentes autohospedadas.

Service worker y datos privados

La política NetworkOnly para páginas, Actions y API evita persistir DNI, ventas o documentos en caché; es una decisión segura y debe conservarse. La PWA offline ofrece solo fallback y borrador local. Hay que validar headers específicos del SW, actualizaciones, rollback y mensajes de reconexión; no cachear respuestas autenticadas para “sentir” velocidad.

Instalación

Manifest, standalone, orientación, iconos 192/512, Apple touch y maskable están presentes. Falta probar el safe zone del maskable, instalación real, actualización, lanzamiento por shortcuts y prompt después de una acción de valor; iOS hoy puede mostrar la guía en la primera visita, contradiciendo la especificación.

Medición dinámica diagnóstica

En desarrollo, la navegación interna dashboard → ventas tardó 3.08–3.17 s hasta mostrar el título, incluso con caché caliente. Los logs del servidor atribuyeron normalmente 0.50–1.21 s al código de aplicación por ruta; empresas llegó a 0.99 s, usuarios a 0.86 s y ventas a 1.20 s. El dashboard recargado registró First Meaningful Paint aproximado de 1.10 s y DOMContentLoaded de 1.51 s. No son cifras de producción, pero demuestran que el cuello no es solo animación.

Red, archivos y consola

La miniatura del comprobante tardó 2.9 s: 2.4 s fueron código de aplicación antes del redirect, por lo que necesita URL firmada/metadata y miniatura optimizada sin bloquear. La consola repitió errores de Base UI por renderizar como no-button en CabeceraPuntoVenta, EmpleadosClient y AccionCambiarPassword; debe corregirse la semántica nativa antes del rediseño.

Presupuesto de aceptación inicial

En el percentil 75 móvil: LCP ≤2.5 s, INP ≤200 ms y CLS ≤0.1. En navegación caliente, feedback visual en el mismo frame y shell de destino visible en ≤200 ms p95. Medir JS comprimido por ruta y fijar el límite después del baseline; como guardrail inicial, compartido ≤180 KB gzip y adicional normal ≤80 KB gzip, con excepción documentada para dashboard.

Orden recomendado de ejecución

El orden reduce retrabajo y convierte la protección del desktop en una condición continua, no en una revisión final.

Fase 0 · medir

Contrato verificable

PERF-01 y QA-01. Baseline móvil, presupuestos y capturas desktop antes de modificar primitivas.

Fase 1 · cimentar

Sistema móvil

MOB-01 a 06 y CORE-01. Shell, barra, sheets, interacción, estados y conectividad.

Fase 2 · acelerar

App Shell y bundle

PERF-02/03. Navegación instantánea comprobada y carga diferida basada en medición.

Fase 3 · migrar

Flujos reales

UI-03/04 primero; luego UI-01/02/05/06/07. Un flujo completo y probado antes del siguiente.

Fase 4 · pulir

Instalación y motion

CORE-02 y MOTION-01. Dispositivos físicos, transición coherente y rollout controlado.

Definition of Done común

  • 320 px sin scroll horizontal y 390/430 px sin solapes.
  • Todos los targets táctiles propios ≥44×44 px; texto/inputs con contraste y zoom iOS controlado.
  • Claro, oscuro, reduced motion, teclado visible y safe areas probados.
  • Carga, vacío, error, offline y pendiente definidos.
  • Sin datos autenticados nuevos en caché del service worker.
  • Baseline desktop ≥1024 px sin diferencias no aprobadas.
  • Tests unitarios/E2E y criterios específicos del issue aprobados.
No hacer

No habilitar Cache Components globalmente, cachear RSC autenticado, reemplazar todas las primitivas desktop, añadir animaciones decorativas o implementar veinte pantallas en un único PR. Cada cambio necesita métrica, fallback y rollback.
